## Быстрый старт

```bash
pip install -r requirements.txt
cp .env.example .env      # ключ AITunnel нужен только для LLM-шагов протокола
```

`ffmpeg` в PATH желателен; если его нет, `imageio-ffmpeg` подставит свой.

### Пайплайн по ТЗ (HEX-JSON)

```bash
py run_local.py meeting.mp3 --model base -o result.json
```

Четыре шага: ASR → диаризация → постобработка текста → сборка JSON.

Язык определяется автоматически (Whisper сам его находит и печатает в stderr).
Если язык известен — лучше указать явно, это исключает ошибки определения:

```bash
py run_local.py meeting.mp3 --language ru
```

Полезные флаги:
`--speakers 3` (если число спикеров известно), `--skip-diarization`, `--no-llm`.

### Качество

```bash
py make_testdata.py            # сгенерировать контрольный набор (Windows, SAPI)
py evaluate_diarization.py     # DER по контрольному набору
py -m pytest tests -q          # 207 тестов без моделей и сети
py -m pytest tests -q --cov=. --cov-report=term-missing   # покрытие (нужен pytest-cov)
```

Покрытие на момент последней проверки — 62% по всем модулям; ключевые
(`metrics` 98%, `audio_utils` и `diarize` 89%, `run_local` 88%, `output` 82%,
`llm` 80%) проверены полностью. Тесты не требуют моделей и сети: тяжёлые шаги
подменяются заглушками, поэтому прогон занимает секунды.

## Метрики (замерено на контрольном наборе)

| Метрика | Значение | Как получено |
|---|---|---|
| DER | **0.0000** | 1, 2 и 3 спикера, DER с исключением стыков ±0.25 с |
| WER русский | **0.092** | модель `base`, 8 фраз |
| WER английский | 0.054 | модель `base` |
| RTF | 0.05–0.17 | быстрее реального времени |

### Масштабирование на длинных записях

Проверено на 10-минутном файле:

| Этап | Время | RTF |
|---|---|---|
| ASR (`base`) | 35.7 с | 0.059 |
| Диаризация | 46.6 с | 0.078 |
| Декодирование | 0.2 с | — |

Итого ~1.4 минуты на 10 минут записи. Узкое место — диаризация: 510 вызовов
ECAPA. Ускорена в 1.6 раза группировкой окон по длине, DER при этом не
изменился (0.0432 до и после).

Важно: батчить окна разной длины нельзя. ECAPA чувствительна к длине входа —
один и тот же сигнал с дополнением нулями давал косинус 0.48, и диаризация
сливала двух спикеров в одного. Группировка идёт по точной длине окна.

### Что важно знать про эти цифры

Набор **синтетический**: русские фразы синтезированы через SAPI, три «голоса»
получены сдвигом тона. Это проверка целостности пайплайна, а не точность на
живых встречах. На реальных записях (шум, перекрытие речи, дальний микрофон)
WER и DER будут заметно выше.

**Размер модели меняет результат по-разному для языков:**

| Модель | WER RU | WER EN | RTF |
|---|---|---|---|
| `tiny` | 0.154 | 0.000 | 0.05–0.11 |
| `base` | **0.092** | 0.054 | 0.05–0.17 |
| `small` | — | 0.151 | 1.25 |

`small` работает **хуже** `tiny` и медленнее реального времени. Дефолт `base`
оправдан; «больше модель — не всегда лучше».

## Шумоподавление (`denoise.py`)

Включается флагом `--denoise`. Метод — спектральное вычитание (Boll, 1979)
плюс режекторный фильтр на 50 Гц и гармоники. Только numpy и scipy, без
нейросетей.

**Что показали замеры** (WER модели `base`, обе стороны через одинаковый WAV):

| Запись | SNR | до | после | итог |
|---|---|---|---|---|
| чистая | 60 дБ | 0.138 | 0.138 | пропущено |
| белый шум, 0 дБ | 6.6 дБ | 0.277 | **0.231** | лучше |
| белый шум, −5 дБ | 3.6 дБ | 0.508 | 0.508 | пропущено |
| розовый шум, 5 дБ | 13.6 дБ | 0.108 | **0.092** | лучше |
| гул 50 Гц, 5 дБ | 10.5 дБ | 0.108 | 0.123 | хуже |
| гул 50 Гц, 10 дБ | 15.2 дБ | 0.108 | **0.092** | лучше |

Отсюда три защитных правила, встроенных в `denoise()`:

1. **Чистую запись не трогаем** (SNR > 25 дБ). Проверено: изменение ровно
   0.0000, ни одного отсчёта.
2. **Слишком сильный шум не трогаем** (SNR < 5.5 дБ). При −5 дБ вычитание
   режет речь: WER рос с 0.52 до 0.82.
3. **Если обработка не улучшила SNR — возвращаем исходник.**

Причина: агрессивное вычитание повреждает речь, а чистый WAV Whisper и так
переносит хорошо. Все три случая выше — это случаи, где фильтр отказывается
работать, и это правильное поведение.

Честное ограничение: это не нейросетевой денойзер. На записях с чужой речью
или музыкой поверх голоса выигрыша не будет.

**Важно про измерения:** WER чувствителен к пересохранению в 16-битный WAV —
один и тот же сигнал давал 0.092 и 0.108. Поэтому все сравнения выше сделаны
через одинаковый путь записи, иначе разница фильтра тонула бы в этом шуме.

## Надёжность ASR

Пять проблем, найденных замерами, устранены в `asr.py`:

| Проблема | Было | Стало |
|---|---|---|
| Воспроизводимость | 18, 18 и **21** сегмент на одном файле | стабильно 15 |
| Язык | `"ru"` жёстко → на англ. аудио выдумывал русский текст | автоопределение |
| Загрузка модели | 0.5–0.95 с на каждый вызов | кэш (повтор — 0 мс) |
| Ошибки ввода | сырой traceback PyAV | «Аудиофайл не найден» |
| `float16` на CPU | `ValueError` | понижается до `int8` |

Причина недетерминированности: faster-whisper по умолчанию включает
temperature-fallback — при неуверенности модель переключается на случайную
выборку. С `temperature=0.0` fallback выключен.

Пример галлюцинации из-за жёсткого языка — английская фраза превращалась в
русскую, хотя в аудио её не было:

```
язык задан "ru":  «Добрый день. Мы need to discuss the release...»
автоопределение:  «Good morning everyone. We need to discuss the release...»
```

Проверка: `py -m pytest tests/test_asr.py -q` (22 теста, без моделей).

## Фильтр галлюцинаций

Whisper на тишине и в конце записи додумывает фразы («Thank you for watching.»,
«Продолжение следует»). На контрольном наборе такой сегмент занимал
123–127 с при длительности записи 123.8 с — то есть выходил за конец файла.

Защита в три слоя:

1. **`asr.py`** — `is_hallucination()`: отбрасывает сегменты за концом аудио и с
   `no_speech_prob > 0.60`, плюс список фраз-заглушек.
2. **`output.py`** — `validate_hex(data, duration_ms)` проверяет физику, а
   `build_result(..., duration_ms=...)` выбрасывает сегменты за границей записи.
3. **`android/.../whisper_jni.cpp`** — та же проверка границ на нативном уровне.

Пороги взяты из замеров, а не наугад: у живой речи `no_speech_prob` не превышал
0.063, у галлюцинации был 0.938. Признаки `compression_ratio` и `avg_logprob`
в фильтр **не** включены — замеры показали, что они не разделяют случаи и дают
только ложные срабатывания (у галлюцинации `compression=0.74`, у живой речи до 2.65).

Проверка фильтра: 1 галлюцинация отброшена, 0 ложных срабатываний на 42
сегментах живой речи.

### Длительность аудио — откуда берётся

Защита границ работает только если известна длительность записи. Здесь была
дыра: `metrics.audio_duration_sec` читает только WAV (модуль `wave`), на mp3
падает с «file does not start with RIFF id». `run_local.py` ловил исключение,
`duration_ms` становился `None`, и проверка границ **молча отключалась** — то
есть на самом частом формате защита не работала.

Теперь длительность берётся через `asr.audio_duration_sec` (ffmpeg/PyAV, понимает
любой формат), а `metrics.audio_duration_sec` остаётся резервом. Если не удалось
определить ни одним способом, в stderr выводится предупреждение, а не тишина.
Регрессия закрыта тестами `tests/test_duration.py`.

## Диаризация: три бэкенда

`diarization.py` выбирает первый доступный бэкенд, чтобы пайплайн не падал:

| Бэкенд | Требует | Качество |
|---|---|---|
| `pyannote` | `pyannote.audio` + `HF_TOKEN` (gated-модель) | эталонное |
| `speechbrain` | `torch` + `speechbrain`, ~80 МБ весов | DER 0.00 на контроле |
| `mfcc` | только numpy | слабое, аварийное |

Почему так: `pyannote/speaker-diarization-3.1` — gated-модель, без `HF_TOKEN`
она не загружается, и пайплайн падал на шаге 2. Теперь при отсутствии токена
берётся `speechbrain`, а если нет и его — `mfcc`.

Явный выбор: `DIARIZATION_BACKEND=speechbrain` (или `pyannote`, `mfcc`).
Принудительный выбор недоступного бэкенда даёт понятную ошибку, а не тихий откат.

## Постобработка текста (`llm.py`)

Два режима, выбор автоматический:

- **`llama`** — llama.cpp + GGUF-модель (Gemma-2-2B, Phi-3-mini, Qwen2.5).
  Нужен `llama-cpp-python` и файл модели (`LLM_MODEL_PATH`).
- **`rules`** — без модели: капитализация, терминальная пунктуация, снятие
  повторов и лишних пробелов, словарь частых ошибок ASR. Работает всегда.

Защита от порчи смысла: если модель изменила больше 45% слов, правка
откатывается к правилам. ТЗ прямо запрещает перефразировать.

## Android (`android/`)

**Важное ограничение:** у `ctranslate2` (ядро faster-whisper) **нет Android-колёс** —
только `manylinux` и `win`. Проверено по индексу PyPI. Поэтому Python-пайплайн
на устройство напрямую не переносится.

Выбранный путь — `whisper.cpp` через JNI (реально собирается под arm64).
В `android/` лежит каркас проекта: Kotlin-экран, JNI-обвязка, конвертация аудио
через `MediaCodec`, сборка HEX-JSON.

**Статус:** APK не собран и не запускался — в окружении разработки нет Android SDK,
Gradle и JDK 17. Подробности и шаги сборки — в `android/README.md`.

## Как подключить к своему проекту

Три модуля ТЗ работают как обычная библиотека — интерфейсы плоские, вход и
выход в формате ТЗ (словари с `start_ms/end_ms/text/speaker_id`):

```python
import sys
sys.path.insert(0, "/путь/к/Xakton-ot-MIFE")

import diarization, llm, output

segments = [{"start_ms": 0, "end_ms": 4000, "text": "добрый день коллеги"}]

segments = llm.clean_segments(segments, backend="rules")        # текст
segments = diarization.diarize("meeting.mp3", segments)         # speaker_id
result   = output.build_result(segments, duration_ms=10_000)    # HEX-JSON
output.save_result(result, "result.json", duration_ms=10_000)   # с валидацией
```

Проверено прогоном из стороннего каталога: `diarize` возвращает те же ключи,
что пришли, плюс `speaker_id`; `build_result` выдаёт результат, который
`validate_hex` принимает. Внешних зависимостей для этого минимума —
только `numpy` (`diarization` без torch откатывается на `mfcc`).

Требования к окружению:

| Модуль | Зависимости |
|---|---|
| `output`, `metrics`, `prompts` | только стандартная библиотека |
| `llm` (режим `rules`) | только стандартная библиотека |
| `llm` (режим `llama`) | `llama-cpp-python` + файл GGUF |
| `asr`, `diarize`, `embeddings` | `numpy`, `faster-whisper`, `imageio-ffmpeg` |
| `diarization` (speechbrain) | плюс `torch`, `speechbrain` |

## ВАЖНО: про облачный прототип

Файлы `client.py`, `pipeline.py`, `app.py`, `process_meeting.py` ходят в AITunnel
(gpt-4o-mini + облачный Whisper). Задание запрещает облачные API и передачу аудио
наружу — прототип **не является сдаваемым решением**, это эталон качества и
источник промптов. Сдаётся Android APK с полностью локальной обработкой.

Локальный пайплайн по ТЗ — `run_local.py` + `asr.py` + `diarization.py` +
`llm.py` + `output.py`. Сеть не использует.
