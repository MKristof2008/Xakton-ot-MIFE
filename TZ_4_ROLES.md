## 0. Что поменялось относительно наброска

В наброске (`neuro-stenographer-draft.pdf`) описан веб-сервис на Streamlit + Whisper + облачный Kimi/Claude. **Такое решение не проходит проверку:**

| Требование задания | Набросок | Наше решение |
|---|---|---|
| Работает под Android | ❌ веб | ✅ Kotlin-приложение, APK |
| Всё вычисляется на устройстве | ❌ сервер | ✅ on-device inference |
| Без облачных API для ASR/диаризации/LLM | ❌ Kimi/Claude | ✅ локальные ONNX/GGML-модели |
| Работает без интернета | ❌ | ✅ полностью офлайн |

Из наброска переиспользуем: **разбивку на роли, контракты данных, правила работы, порядок этапов** (заглушки → модули → интеграция → только стабильность) и промпты/метрики из существующих файлов репозитория.

## 1. Цель и результат

Android-приложение, которое локально превращает запись разговора в структурированную расшифровку:

```
выбор аудиофайла (или запись с микрофона)
        ↓
ASR (локальная модель) → текст + таймкоды
        ↓
диаризация (локальная модель) → кто говорит
        ↓
слияние → реплики «Спикер N, 00:01.25–00:04.38: текст»
        ↓
локальная LLM → пунктуация, регистр, исправление ASR-ошибок
        ↓
экран расшифровки + экспорт JSON
```

**Сдаём:** APK, исходники, инструкцию, архитектуру, ограничения, результаты тестов, видео-демо (слайд 19).

**Проверка жюри:** ставят APK → импортируют 3 записи → запускают обработку → экспортируют JSON → считают WER и RTF (слайд 15).

## 3. Формат данных

### 3.1 Выход — строго по ТЗ (слайд 14)

```json
{
  "transcript": [
    { "speaker_id": "speaker_1", "start_ms": 1250, "end_ms": 4380, "text": "Добрый день!" }
  ]
}
```

| Поле | Тип | Правило |
|---|---|---|
| `transcript` | array | массив реплик, по возрастанию `start_ms` |
| `speaker_id` | string | `speaker_1`, `speaker_2`, … нумерация в порядке первого появления |
| `start_ms`, `end_ms` | integer | мс от начала файла, `end_ms > start_ms` |
| `text` | string | непустой, без таймкодов, без имени спикера внутри |

Валидатор уже есть: `output.py::validate_hex()` — перенести правила 1:1 в Kotlin (`TranscriptValidator`).

### 3.2 Внутренний контракт (между модулями)

```kotlin
data class AsrSegment(val startMs: Int, val endMs: Int, val text: String)
data class SpeakerTurn(val startMs: Int, val endMs: Int, val speakerRaw: String)
data class Replica(val speakerId: String, val startMs: Int, val endMs: Int, val text: String)

fun transcribe(audio: FloatArray, sampleRate: Int): List<AsrSegment>          // Р2 + Р3
fun diarize(audio: FloatArray, sampleRate: Int, numSpeakers: Int?): List<SpeakerTurn>  // Р3
fun merge(asr: List<AsrSegment>, turns: List<SpeakerTurn>): List<Replica>     // Р1
fun postprocess(rep: List<Replica>): List<Replica>                            // Р3
fun toHexJson(rep: List<Replica>): String                                    // Р1
```

Правила `merge`: реплика получает спикера с максимальным пересечением по времени; если ASR-сегмент накрывает двух говорящих — разрезать по границе turn'а; если пересечений нет — спикер по ближайшей середине. Логика уже написана в `diarization.py::_best_speaker` — переносить как есть.

### 3.3 Заглушки

Каждый модуль до готовности реализуется заглушкой в `src/debug/`: `FakeAsr` (3 сегмента из примера ТЗ), `FakeDiar` (2 спикера), `FakeLlm` (echo). Это позволяет писать UI и Android-каркас параллельно, не блокируя друг друга.

## 4. Стек и обоснование

| Слой | Выбор | Почему / запасной вариант |
|---|---|---|
| UI | Kotlin + Jetpack Compose, `minSdk 26`, `targetSdk 34` | быстрый UI, есть анимация прогресса; запасной — XML Views |
| Декод аудио | `MediaExtractor` + `MediaCodec` → PCM 16 kHz mono FloatArray | без внешних зависимостей; запасной — FFmpeg-kit (больше APK, но все форматы) |
| ASR | **sherpa-onnx** (Whisper tiny/base/small int8) или **whisper.cpp** через JNI | ONNX Runtime уже нужен для диаризации — один рантайм; whisper.cpp — если нужен максимум контроля над таймкодами |
| VAD | silero-vad ONNX (~2 МБ) | отсекает тишину, ускоряет ASR, улучшает границы |
| Диаризация | **sherpa-onnx speaker-diarization** (pyannote segmentation-3.0 ONNX + WeSpeaker/3D-Speaker embeddings, кластеризация внутри) | полностью офлайн, без HF-токена; запасной — свои эмбеддинги ECAPA + агломеративная кластеризация |
| LLM | **llama.cpp** + GGUF `Qwen2.5-1.5B-Instruct` / `Gemma-2-2B-it` Q4_K_M | требование «локальная LLM» обязательное; запасной — `T-lite-it-1.0` Q4 |
| Метрики | встроенный экран «Тесты» + `metrics.py` на ПК для эталонных замеров | WER/RTF/DER нужны и для отладки, и для отчёта |

**Требования к устройству:** arm64-v8a, ≥ 4 ГБ RAM, ≥ 2 ГБ свободного места (модели ~1–1.5 ГБ суммарно). Указать в README.

### РОЛЬ 1. Капитан / Android-каркас / интеграция

**Цель:** чтобы всё собиралось, запускалось, мерджилось и сдавалось.

**Ответственность:**
- репозиторий, ветки, PR/мерджи, `README`, `.gitignore`;
- Gradle-проект, APK, подпись, установка на устройство;
- JNI-мост, загрузка моделей из `assets/`,WorkManager/foreground service;
- `merge()` и `toHexJson()` — сборка финального результата;
- прогон трёх тестовых записей, сводная таблица метрик;
- итоговая подача: форма, ссылка на репозиторий, APK.

**Файлы:**
```
android/                      Gradle-проект
  app/build.gradle.kts        ABI, упаковка .so и моделей
  app/src/main/assets/models/ веса (или скрипт скачивания)
  app/src/main/cpp/CMakeLists.txt, jni_bridge.cpp
  app/src/main/java/.../MainActivity.kt
  app/src/main/java/.../AudioPipeline.kt   оркестрация, прогресс, отмена
  app/src/main/java/.../AudioDecoder.kt    любой файл → PCM 16 kHz mono
  app/src/main/java/.../Merge.kt, HexJson.kt, TranscriptValidator.kt
docs/ARCHITECTURE.md, docs/LIMITATIONS.md
artifacts/test-results/results.csv
```

**Задачи по этапам:**
1. **Этап 0:** создать Gradle-проект, собрать и поставить на телефон пустой APK. Зафиксировать контракты из раздела 3, раздать роли.
2. Подключить NDK/CMake, собрать нативный hello-world, вызвать из Kotlin через JNI.
3. `AudioDecoder`: импорт через SAF (`content://`), декод в PCM 16 kHz mono, нормализация по амплитуде.
4. `AudioPipeline`: последовательность этапов, прогресс (%), отмена, foreground service + wake lock (иначе ОС убьёт обработку).
5. Упаковка моделей: распаковка `assets → filesDir` при первом запуске, проверка SHA256, прогресс распаковки.
6. `merge()` + `toHexJson()` + валидатор схемы.
7. Сборка release APK, проверка на чистом устройстве в авиарежиме.
8. Прогон трёх записей → `results.csv` (запись, модель, WER, DER, RTF, устройство).

**Готово, когда:** APK ставится на чистое устройство без интернета и выдаёт валидный JSON по трём записям; `results.csv` заполнен; README объясняет, что сдаётся, а что — прототип.

**Блокирует:** всех. Первый час — только эта роль.

### РОЛЬ 2. Аудиопредобработка + ASR + таймкоды

**Цель:** качество текста. **Это 40 + 10 = 50 баллов из 100.**

**Файлы:**
```
android/app/src/main/cpp/asr_jni.cpp, asr_engine.cpp
android/app/src/main/java/.../Asr.kt        загрузка модели, параметры декода
android/app/src/main/java/.../Vad.kt        silero VAD
android/app/src/main/java/.../AudioPre.kt   ресемплинг, громкость, шумоподавление
tools/bench_asr.py                          WER на ПК (эталон)
tests/audio/                                3–4 тестовые записи
tests/reference/                            эталонные JSON-расшифровки
```

**Задачи:**
1. Собрать sherpa-onnx (или whisper.cpp) под `arm64-v8a`, добиться инференса на устройстве на 30-секундном wav.
2. Выбрать модель замером: `tiny`/`base`/`small`, int8/q5_1. Критерий — WER на русском против RTF; результат с цифрами в `docs/ARCHITECTURE.md`.
3. Язык: жёстко `ru` (авто-детект врёт на коротких репликах). `initial_prompt` с лексикой совещаний (протокол, повестка, кворум, поручение).
4. VAD: вырезать тишину, не теряя короткие реплики ≥ 300 мс. Проверить на записи с перебиваниями.
5. **Таймкоды от начала файла.** При чанковании — оффсет чанка прибавлять к каждому сегменту; покрыть тестом.
6. Предобработка: 16 kHz mono, нормализация RMS, high-pass 80 Гц от гула; опционально лёгкий noise-suppression.
7. Собрать 3–4 записи: чистая / шумная / с перебиваниями 3+ спикера / тихая речь. Для каждой — эталонный JSON в `tests/reference/`.

**Готово, когда:** WER ≤ 15 % на чистой записи (цель ≤ 10 %), RTF ≤ 1.0 на тестовом устройстве, смещение таймкодов ≤ 300 мс на 5 контрольных репликах.

**Риск:** `small` втрое медленнее `base`. Точность стоит 40 баллов, скорость — 10, поэтому при конфликте выбираем точность, а RTF держим за счёт VAD + коротких чанков.

### РОЛЬ 3. Диаризация + локальная LLM + постобработка

**Цель:** «кто говорит» (25 баллов) и обязательная локальная LLM.

**Файлы:**
```
android/app/src/main/java/.../Diar.kt        сегментация + эмбеддинги + кластеризация
android/app/src/main/cpp/diar_jni.cpp
android/app/src/main/java/.../LlmPost.kt     локальная LLM
android/app/src/main/cpp/llm_jni.cpp
android/app/src/main/assets/prompts/         промпты из prompts.py
tools/bench_diar.py                          DER на ПК
```

**Задачи:**
1. Диаризация: sherpa-onnx (segmentation-3.0 ONNX + speaker embedding ONNX + агломеративная кластеризация). Порог кластеризации подобрать на тестовых записях.
2. Число спикеров: автоподбор + ручной выбор в UI (1–6). Проверить на 2, 3 и 4 говорящих.
3. Стабильность `speaker_id`: одна персона — один ID на всю запись; нумерация по первому появлению (`output.py::normalize_speakers` — эталон).
4. Слияние с ASR и разрезание сегментов на границах смены говорящего (делает точность меток лучше).
5. Локальная LLM (`llama.cpp`, GGUF Q4): только пунктуация, регистр, явные ошибки ASR. **Запрещено** перефразировать, сокращать, выбрасывать реплики — иначе WER вырастет и сверка с эталоном развалится.
6. Защита от галлюцинаций: если длина ответа отличается от входа > 30 % или появилась латиница/цифры, которых не было, — откат на исходный текст.
7. Промпты: взять `prompts.py` (`LOCAL_BASE_RULES`, `CLEAN_PROMPT`) и адаптировать под 1.5–2B модели: короткий промпт, один пример, строгий формат ответа.

**Готово, когда:** DER ≤ 25 % на тестовых записях, число спикеров определяется верно в авторежиме, постобработка **не увеличивает** WER относительно сырого ASR (мерить до/после), LLM реально вызывается на устройстве в офлайне.

**Риск:** диаризация — самый тяжёлый этап на телефоне. План Б: только 2 спикера, прореживание аудио для сегментатора, упрощённая кластеризация. Делать последней.

### РОЛЬ 4. UI, экспорт, метрики-экран, демо

**Цель:** 10 баллов за UX и всё, что видит жюри.

**Файлы:**
```
android/app/src/main/java/.../ui/ImportScreen.kt
                              .../ui/ProgressScreen.kt
                              .../ui/TranscriptScreen.kt
                              .../ui/TestScreen.kt
android/app/src/main/java/.../export/JsonExporter.kt, TextExporter.kt
artifacts/demo/                            видео, скриншоты, сценарий
docs/SETUP.md                              инструкция по установке
presentation/                               слайды
```

**Задачи:**
1. Экран импорта: SAF-пикер, последние файлы, выбор числа спикеров (авто/2/3/4/5).
2. Экран прогресса: этапы с процентами (декод → распознавание → говорящие → текст), оценка остатка времени, кнопка «Отмена». Обязателен: обработка 5 минут аудио на телефоне идёт минуты.
3. Экран расшифровки: `[MM:SS] Спикер N: текст`, цвет на спикера, поиск по тексту, переключение «с таймкодами / без».
4. Воспроизведение с переходом к реплике (тап по реплике → play с её таймкода) — средний уровень, даёт UX-баллы.
5. Экспорт JSON (валидируется перед сохранением) + TXT/MD бонусом, через `ACTION_CREATE_DOCUMENT`.
6. Экран «Тесты»: прогон встроенных эталонных записей и показ WER/DER/RTF — сильный аргумент на защите.
7. Слайды + сценарий демо 3–4 минуты, обязательно с авиарежимом на экране; записать видео (установка → импорт → обработка → результат → экспорт).

**Готово, когда:** экспорт проходит валидацию схемы; поворот экрана и уход в фон не роняют и не прерывают обработку; видео записано; инструкция проверена человеком «с нуля».

## 7. Этапы и правила

| Этап | Доля времени | Содержание | Выход |
|---|---|---|---|
| **E0. Каркас и контракты** | первый час | проект собирается, контракты зафиксированы, роли разобраны | APK-пустышка на телефоне |
| **E1. Заглушки** | ~30 % | UI и пайплайн целиком работают на `Fake*` | сквозной демо-путь без моделей |
| **E2. Реальные модули** | ~40 % | ASR, диаризация, LLM на устройстве | каждый модуль проходит свой DoD |
| **E3. Интеграция и замер** | ~20 % | прогон трёх записей, сводная таблица, фиксы | `results.csv`, стабильный APK |
| **E4. Только стабильность и демо** | ~10 % | новые фичи запрещены; только фиксы, видео, слайды | сдача |

**Правила:**
- каждый работает в своей ветке (`feat/asr`, `feat/diar`, `feat/llm`, `feat/android`, `feat/ui`), мердж в `main` — через PR или с ревью второго участника;
- коммит после каждого рабочего шага;
- секреты только в `.env`, в репозиторий не попадают (для финальной сборки они не нужны вообще);
- `app.py`-подобных «всё в одном файле» не пишем: UI отдельно, логика отдельно;
- тяжёлые модели в `.gitignore`; в репозитории — скрипт скачивания с именами файлов и SHA256;
- стендап раз в 2–3 часа: сделано / блокер / дальше.

## 10. Отчётность и структура репозитория

По шаблону жюри `grigorevmp/hacathon_template`:

```
README.md                 что это, как собрать, что сдаётся
TZ.md / docs/             это ТЗ, архитектура, ограничения, тесты
src/                      исходники Android-проекта
artifacts/
  app-release.apk         собранный APK
  demo/                   видео, скриншоты
  test-results/           results.csv + эталонные расшифровки
config/example.env        не нужен для офлайн-сборки (оставить пустым)
```

Чек-лист сдачи: APK · исходники · инструкция по установке · архитектура и модели · ограничения · результаты тестов · видео-демо · ссылка на репозиторий.

**Чек-лист защиты (5 баллов):** авиарежим включён до старта обработки · названы модели и цифры, почему они · показан `results.csv` · названы ограничения (устройство, число спикеров, длина записи, где деградирует) · объяснено, что делает LLM и как она не может испортить транскрипт.
