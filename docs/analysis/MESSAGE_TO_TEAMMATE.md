## Главное: прогоны run-001..003 недействительны для сравнения моделей

| Прогон | Модель | RTF на SM-S938B (Debug-сборка!) | Проблема замера |
|---|---|---|---|
| run-001 | ggml-small | 16.44 | другая запись (31.5 с), без эталона |
| run-002 | ggml-base | 5.88 | другая запись (13.6 с), без эталона |
| run-003 | ggml-tiny | 3.85 | другая запись (25.6 с), без эталона |

Разные записи + assembleDebug (неоптимизированный нативный код) → вывод
«тупик» снят. Честный ответ даст Release-сборка (-O3, NEON) на едином наборе
записей с эталонами. sherpa-onnx остаётся сильным кандидатом (VAD и
диаризация из коробки), но обосновать выбор нужно замерами, а не впечатлением.

## Что готово с моей стороны и пригодится в main

1. `ml/llm.py` + `ml/prompts.py` — протокол совещания локальной LLM
   (summary/темы/решения/задачи/ответственные/сроки, JSON-валидация + retry,
   chunk/merge, таймкоды у задач, 22 теста). **Внимание: дублирование** —
   в main есть корневой `llm.py`; при слиянии надо выбрать один (мой имеет
   JSON-схему и тесты).
2. Инфраструктура живых прогонов: лог транскрипта в logcat
   (тег WhisperJNI, маркеры BEGIN/END) — перенесу на sherpa-onnx движок,
   чтобы архив `docs/runs/` продолжал пополняться.
3. Графики и реестр ошибок — обновляются скриптами из таблиц, можно
   подключить к твоим замерам.
